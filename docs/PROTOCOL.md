# PROTOCOL — доска распределения задач между воркспейсами (полная спецификация)

Версия: 1.0. Статус: согласован с владельцем. Автор: workflow (default-workspace).
Это контракт для реализатора плагина dsh-kanban-board. Всё, что не описано здесь явно, реализовывать
запрещено; неоднозначность — повод задать вопрос, а не додумать.

# 1. Область

Плагин dsh-kanban-board — механизм канбана, распределяющего работу между воркспейсами реалма, а не между
сессиями одного воркспейса. Плагин ничего не знает про конкретный реалм заранее: воркспейсы, их папки обмена
и роль архитектора задаёт конфиг реалма (§3). Плагин не исполняет задачи — исполнением занимается движок
workflow в каждом воркспейсе (docs/tasks, гейты, приёмка, релиз).

# 2. Словарь

Реалм — набор воркспейсов, объединённых одной работой; описывается конфигом реалма (§3).
Архитектор — воркспейс-оркестратор реалма: владелец доски и журнала; принимает стыки, закрывает эпики.
Исполнитель — воркспейс, который берёт наряд и делает работу под своим движком workflow.
Эпик — сквозная задача реалма; единица согласования и приёмки.
Наряд — кусок работы для одного воркспейса; единица движения по доске.
Подзадача — дробление наряда внутри воркспейса; живёт в его движке, не на доске.
Карточка — файл эпика или наряда на доске архитектора.
Письмо — файл в папке обмена, формат dsh-exchange/1 (§6).
Журнал — append-only файл board/journal.jsonl, фиксирует все переходы и события (§8).
Мотор — host-половина плагина: применяет переходы, гоняет обход, чинит доску (§9).
Задействованный воркспейс — воркспейс, у которого есть наряд в эпике ИЛИ чей контракт обмена затрагивается.
Читатель контракта — воркспейс, который читает чужой контракт, но ничего не реализует; не задействован.

# 3. Конфиг реалма

Файл JSON в воркспейсе архитектора; путь задаётся при монтировании плагина. Схема (поля и типы):

    version : number = 1 — версия схемы конфига;
    name : string — имя реалма (для отображения);
    agreeTimeoutMinutes : number = 15 — дефолт срока согласования эпика;
    architect : { root : string, exchange : string } — корень и папка обмена архитектора;
    workspaces : [ { id : string, root : string, exchange : string } ] — исполнители.

Правила:
- id воркспейса уникален в реалме; совпадает с именем папки обмена и используется в полях карточек;
- exchange — абсолютный путь к папке обмена воркспейса (каталог, содержащий outbox/);
- у архитектора тоже есть workspaces-запись, если он сам исполняет наряды; иначе только поле architect;
- изменение конфига (добавление/удаление воркспейса) — это отдельная версия конфига, а не тихая правка;
  плагин при загрузке проверяет version и неизвестные поля игнорирует, но отсутствующие обязательные — ошибка.

Пример: examples/realm.example.json (console/proxy/optimizer — плейсхолдеры, реальные пути подставляет владелец).

# 4. Карточки

## 4.1 Карточка эпика — board/epics/<EPIC>.md

Машинные поля в мета-блоке JSON в HTML-комментарии в начале файла; тело — описание для человека.

    id : string — системный UUID: генерирует плагин при создании, пользователь его не вводит;
    title : string;
    status : enum — draft | agreeing | agreed | decomposed | in-progress | accepted | done | blocked | needs-decision;
    involved : string[] — id задействованных воркспейсов;
    agreed : { <id-воркспейса> : { at : ISO, contracts : string[], criteria : string } } — зафиксированные согласия;
    agree_until : ISO — срок согласования; если не задан, применяется agreeTimeoutMinutes конфига;
    contracts : string[] — версии контрактов обмена, действующие в эпике;
    scenario : string — ссылка/описание эталонной серии (стык стадий);
    created, updated : ISO;
    revision : number — растёт на каждую правку эпика.

## 4.2 Карточка наряда — board/tasks/<EPIC>-<N>.md

    id : string — системный UUID (генерирует плагин), пользователь его не вводит;
    title : string — короткое человеческое название наряда;
    epic : string — id эпика;
    workspace : string — id воркспейса-исполнителя;
    role : string | null — роль внутри воркспейса, если их несколько;
    status : enum — proposed | agreed | in-progress | integration | accepted | rework | blocked | needs-decision;
    owner : string | null — id сессии исполнителя (если воркспейс отдал);
    lease_until : ISO | null — до какого момента наряд считается взятым;
    blocked_by : string[] — id нарядов, блокирующих этот;
    contracts : string[] — версии контрактов, которые обязан соблюсти наряд;
    evidence : string[] — ссылки на письма/артефакты, доказывающие готовность;
    subtasks : { done : number, total : number } — счётчик подзадач;
    created, updated : ISO;
    revision : number — растёт на каждый переход.

Инварианты полей:
- revision строго монотонный; переход с revision, меньшим текущего, отклоняется (stale);
- subtasks.done не больше subtasks.total; total задаёт [subtask-plan], done увеличивает [subtask-done];
- owner и lease_until появляются и исчезают вместе: взятие наряда ставит оба, возврат (просрочка) снимает оба.

# 5. Состояния и переходы

## 5.1 Состояния эпика

    draft         — заведён архитектором, участники не подтвердили;
    agreeing      — ждём [agree-epic] от всех involved;
    agreed        — все согласовались, декомпозиция разрешена;
    decomposed    — наряды созданы;
    in-progress   — хотя бы один наряд не терминален;
    accepted      — все наряды accepted, цепочка стыков и эталонная серия зелёные;
    done          — эпик закрыт;
    blocked       — есть наряд в blocked без решения;
    needs-decision — требует вердикта архитектора (таймаут согласования, тупик зависимостей).

Переходы эпика (кто применяет):

    draft -> agreeing       архитектор, при старте согласования;
    agreeing -> agreed      мотор, когда agreed содержит все involved;
    agreeing -> needs-decision  мотор, по истечении agree_until;
    agreed -> decomposed    архитектор, после создания нарядов;
    decomposed -> in-progress  мотор, когда первый наряд перешёл в in-progress;
    in-progress -> accepted  мотор, когда все наряды accepted;
    accepted -> done        архитектор (эталонная серия зелёная, решение закрыть);
    accepted -> rework      архитектор, по [scenario-failed];
    любое -> blocked        мотор, когда есть наряд в blocked;
    blocked -> needs-decision  архитектор.

## 5.2 Состояния наряда

    proposed      — создан при декомпозиции;
    agreed        — контракты стыка согласованы для этого наряда;
    in-progress   — взят в работу (есть owner и lease_until);
    integration   — результат стадии предъявлен на стык;
    accepted      — стык принят архитектором;
    rework        — возврат на доработку;
    blocked       — заблокирован, ждёт другой наряд/решение;
    needs-decision — нужен вердикт архитектора.

Переходы наряда (кто применяет, триггер, условия):

    proposed -> agreed        архитектор, после [interface-agreed] по всем стыкам наряда;
    agreed -> in-progress     мотор, по [task-accept] с валидным lease_until;
    in-progress -> integration мотор, по [stage-ready] с непустым evidence;
    integration -> accepted   архитектор, вердикт по стыку;
    integration -> rework     архитектор, отказ стыка;
    accepted -> rework        архитектор, по [scenario-failed];
    in-progress -> agreed     мотор, по истечении lease_until;
    любое -> blocked          мотор, по [blocked] с причиной;
    blocked -> agreed         архитектор, после снятия блокировки;
    blocked/needs-decision -> agreed  архитектор.

Не указанный в таблице переход — запрещён. Переход предлагает исполнитель письмом, применяет мотор или
архитектор; исполнитель карточку и журнал не пишет никогда.

# 6. Письма

## 6.1 Формат

dsh-exchange/1. Шапка: From, To, Date, Thread, Status, Workspace, Session, Reply-To (для ответов), Subject.
Session обязателен в любом письме: сторону определяют по нему, а не по From. Thread: threads/kanban-<EPIC>/.

## 6.2 Маркеры — префикс Subject

От исполнителя архитектору:

    [agree-epic]      — согласие с эпиком и своей частью; payload: contracts[], criteria, срок;
    [interface-agreed]— подтверждение версии контракта обмена для наряда; payload: наряд, версии;
    [task-accept]     — взятие наряда; payload: наряд, lease_until;
    [stage-ready]     — результат стадии; payload: наряд, evidence[];
    [blocked]         — блокировка; payload: наряд, причина, blocked_by[];
    [needs-decision]  — запрос вердикта; payload: наряд, вопрос;
    [subtask-plan]    — план подзадач; payload: наряд, total, список подзадач;
    [subtask-done]    — выполнена подзадача; payload: наряд, номер/имя подзадачи;

От архитектора исполнителю (ответы мотора или архитектора):

    [transition-applied] — переход применён; payload: наряд, from, to, ссылка на строку журнала;
    [transition-rejected]— отказ; payload: наряд, причина, допустимые переходы;
    [duplicate]         — письмо уже обработано (повтор без изменения состояния);
    [unknown-card]      — карточка не найдена;
    [lease-expired]     — лиз истёк, наряд возвращён в agreed;
    [epic-invite]       — приглашение к согласованию эпика; payload: epic, title, contracts, agree_until;
    [subtask-approved] / [subtask-rejected] — вердикт по плану подзадач;
    [board-repaired]    — доска восстановлена из журнала после расхождения.

## 6.3 Подтверждение

Каждый переход подтверждается ответным письмом: исполнитель не гадает по молчанию. Повтор письма (та же
сессия, тот же наряд, тот же маркер, тот же payload) даёт [duplicate] и не меняет состояние.

# 7. Повторное согласование

Если в ходе эпика меняется задача или версия контракта обмена, пересогласование выполняется только с
воркспейсами, которых касается пересогласованная задача; остальные сохраняют зафиксированное согласие.
Маркер тот же [agree-epic], в теле письма указывается, какая задача/контракт пересогласовывается и какой
становится новая версия. Мотор сбрасывает agreed только для затронутых воркспейсов и снова ждёт их.

# 8. Журнал (board/journal.jsonl)

Append-only, одна строка JSON на событие. События и схемы:

    kind=transition: { at, kind, epic, card, from, to, by, letter, proof, lease_until?, revision }
    kind=agree:      { at, kind, epic, workspace, contracts[], criteria, letter }
    kind=subtask:    { at, kind, epic, card, delta_done, letter }
    kind=sweep:      { at, kind, summary: { applied, rejected, expired }, letter? }
    kind=repair:     { at, kind, epic?, card?, from, to, reason }

Правила:
- порядок записи — карточка сначала (временный файл + rename), затем строка журнала;
- журнал не редактируется; расхождение карточка<->журнал чинит replay (§9.3), журнал — источник правды;
- идемпотентность перехода: ключ <card>:<from>:<to>:<sha256(нормализованный payload письма)>, хранится
  в board/.sweep.json и проверяется перед записью.

# 9. Мотор

## 9.1 apply(card, from, to, reason, letter)

1. Найти карточку; нет — письмо [unknown-card].
2. Проверить, что from совпадает с текущим status и revision актуален; иначе [transition-rejected] со
   списком допустимых переходов.
3. Проверить переход по таблице §5; проверить payload (у stage-ready — непустой evidence, у task-accept —
   lease_until в будущем).
4. Проверить идемпотентность по ключу; если уже был — [duplicate].
5. Записать карточку (temp+rename), обновить status/owner/lease/evidence/subtasks/revision.
6. Дописать строку журнала kind=transition.
7. Ответить [transition-applied].

Одна операция — одна карточка — одна строка журнала. Никаких пакетных правок.

## 9.2 sweep (обход)

Триггеры: таймер, приход письма, перед рендером. Шаги:
1. Прочитать новые письма из outbox каждого воркспейса (память прочтения в .sweep.json).
2. Для каждого письма — apply(...) с разбором маркера.
3. Проверить лизы: lease_until < now -> вернуть в agreed, снять owner/lease, письмо [lease-expired].
4. Проверить agree_until эпиков в agreeing -> needs-decision при истечении.
5. Записать строку kind=sweep с итогом (применено/отклонено/просрочено).

Идемпотентность: повторный проход по тем же письмам ничего не меняет.

## 9.3 replay/reconcile

Карточка — материализованное представление журнала. При расхождении status с последней строкой журнала:
восстановить из журнала, записать kind=repair, письмо [board-repaired]. Это делает код, а не модель.

# 10. Разделение код/модель

Код (детерминировано, без суждения): валидация переходов и revision, проверка payload и evidence,
идемпотентность, запись карточки и журнала, обход, лизы, таймаут согласования, счётчик подзадач,
сверка/починка, рендер.

Модель (суждение, только через apply/accept): выбор версии контракта, приёмка стыка (integration->accepted,
integration->rework), закрытие эпика (accepted->done), декомпозиция на наряды, приоритеты и назначение,
вердикт по подзадачам (subtask-approved/rejected).

Модель меняет состояние только операцией apply с by=architect и строкой журнала; прямая правка карточки —
дефект, ловится сверкой journal<->tasks.

# 11. Инварианты

1. Карточки и журнал пишет только архитектор (мотор/сессия архитектора).
2. Письма — каждый в свой outbox; чужие outbox только читаются.
3. Журнал append-only и не редактируется.
4. Карточка восстанавливается из журнала (журнал — источник правды).
5. Любой переход имеет подтверждающее письмо и строку журнала.
6. revision строго монотонный на карточку.
7. subtasks.done <= subtasks.total; увеличение только по [subtask-done].
8. owner и lease_until связаны (появляются/снимаются вместе).
9. Эпик не переходит в работу, пока не agreed всеми involved.
10. Правка состояния в обход apply — дефект.

# 12. Граничные случаи (обязательные к обработке)

- Письмо с неизвестным маркером -> не применять, ответ [transition-rejected] с причиной.
- Письмо о несуществующей карточке -> [unknown-card].
- Повтор письма -> [duplicate], состояние не меняется.
- Письмо с недопустимым переходом -> [transition-rejected] + список допустимых.
- Письмо с устаревшим revision -> [transition-rejected] (stale).
- stage-ready без evidence -> [transition-rejected].
- task-accept с lease_until в прошлом -> [transition-rejected].
- Истёкший лиз -> авто-возврат в agreed + [lease-expired].
- Истёкший agree_until -> needs-decision.
- Цикл blocked_by (A ждёт B, B ждёт A) -> детект цикла, эпик/наряды в needs-decision.
- Дубликат наряда (тот же id) -> ошибка конфигурации доски, не перезаписывать.
- Письмо из воркспейса, отсутствующего в конфиге -> игнорировать + [unknown-card] отправителю.
- Письмо без Session -> не обрабатывать (сторону не определить).
- Расхождение journal<->tasks -> replay, kind=repair, [board-repaired].
- Смена версии конфига реалма -> перечитать; пропавший воркспейс: его наряды в needs-decision.

# 13. Версионирование протокола

Поле version в начале документа и в конфиге реалма. Изменение формата карточки, состояний, маркеров,
журнала или конфига — новая версия протокола, а не тихая правка. Плагин объявляет поддерживаемые версии;
доска с неподдерживаемой версией протокола — не трогается и сигнализирует об ошибке.

# 14. Сквозной пример (эпик от заведения до done)

1. Архитектор создаёт эпик E1 (involved: console, proxy, optimizer; agree_until = +15 мин).
2. console, proxy, optimizer присылают [agree-epic] каждый со своим Session; мотор фиксирует agreed.
3. agreed достигнут -> мотор переводит E1 в agreed; архитектор раскладывает на наряды E1-1, E1-2, E1-3.
4. Для каждого наряда стороны согласуют версии контрактов ([interface-agreed]); наряд -> agreed.
5. console присылает [task-accept] по E1-1 с lease_until -> мотор ставит in-progress.
6. console разложил наряд: [subtask-plan] -> архитектор [subtask-approved]; console шлёт [subtask-done] по мере.
7. console присылает [stage-ready] с evidence -> E1-1 -> integration.
8. Архитектор принимает стык: E1-1 -> accepted; аналогично proxy, optimizer.
9. Все наряды accepted -> мотор переводит E1 в accepted; архитектор прогоняет эталонную серию и закрывает -> done.

# 15. Формат ответов архитектора

Каждый ответ — письмо [перечисленный маркер] со ссылкой на письмо-запрос (Reply-To) и, где есть переход,
ссылкой на строку журнала. Тело ответа — факты: что изменено, причина отказа, список допустимых переходов.

# 16. Что вне области протокола

- формат манифеста плагина и его монтаж в профиль — отдельный документ (docs/SETUP.md);
- внутренняя кухня исполнения в воркспейсе (docs/tasks, гейты) — движок workflow, не доска;
- рендер/панель — реализация плагина, но данные для рендера — только из карточек и журнала.
