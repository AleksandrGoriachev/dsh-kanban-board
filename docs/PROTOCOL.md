# PROTOCOL — доска распределения задач между воркспейсами (плагин dsh-kanban-board)

Версия протокола: 1. Автор: workflow (default-workspace). Это контракт, который читает и реализует
исполнитель кода плагина; сам протокол кодом не является.

## 1. Назначение и границы

Плагин «dsh-kanban-board» — механизм канбана, распределяющего работу между воркспейсами реалма, а не
между сессиями одного воркспейса. Плагин ничего не знает про конкретный реалм заранее: список воркспейсов,
их папки обмена и роль архитектора задаёт конфиг реалма (§9). console/proxy/optimizer — пример, не данные.

Плагин не исполняет задачи: исполнением занимается движок workflow в каждом воркспейсе (docs/tasks, гейты,
приёмка, релиз). Плагин только оркестрирует распределение.

## 2. Термины

- Реалм — набор воркспейсов, объединённых одной работой.
- Архитектор — воркспейс-оркестратор реалма: ведёт доску, принимает стыки, закрывает эпики.
- Исполнитель — воркспейс, который берёт наряд и делает работу под своим движком.
- Эпик — задача реалма (сквозная): цель, стадии, контракты обмена, эталонный сценарий.
- Наряд — кусок работы для конкретного воркспейса; двигается по доске.
- Карточка — файл наряда на доске архитектора.
- Письмо — файл в папке обмена, формат dsh-exchange/1.
- Журнал — append-only файл переходов доски.

## 3. Расположение

Доска живёт в воркспейсе архитектора отдельным каталогом board/ (не внутри docs/tasks и не в движке):

    board/
      epics/<EPIC>.md
      tasks/<EPIC>-<N>.md
      journal.jsonl
      .sweep.json

Папки обмена — по одному outbox у каждого воркспейса, соседи читают по конфигу реалма (§9).
Письмо пишется только в свой outbox; чужие outbox только читаются.

## 4. Формат карточки

Карточка — один файл tasks/<EPIC>-<N>.md. Машинные поля — мета-блок JSON в HTML-комментарии в начале,
человекочитаемое тело ниже. Поля:

    id           — <EPIC>-<N>
    epic         — идентификатор эпика
    workspace    — id воркспейса-исполнителя из конфига реалма
    role         — роль (опционально, если у воркспейса несколько ролей)
    status       — состояние (§5)
    owner        — id сессии исполнителя (если воркспейс его отдал)
    lease_until  — ISO-8601, до какого момента наряд считается взятым
    blocked_by   — массив id нарядов, которые блокируют этот
    contracts[]  — версии контрактов обмена, которые обязан соблюсти наряд
    evidence[]   — ссылки на письма/артефакты, доказывающие готовность
    created, updated — ISO-8601
    revision     — монотонный счётчик, растёт на каждый переход

Источник правды о статусе — карточка; журнал — доказательство переходов. При расхождении прав журнал.

## 5. Состояния и переходы

Состояния: proposed, agreed, in-progress, integration, accepted, done, blocked, needs-decision, rework.

Допустимые переходы и кто их применяет:

    proposed -> agreed          архитектор, после [interface-agreed] от всех участников стыка
    agreed -> in-progress       мотор автоматически, по [task-accept] с валидным лизом
    in-progress -> integration  мотор автоматически, по [stage-ready]
    integration -> accepted     архитектор, по решению о стыке
    integration -> in-progress  архитектор, отказ стыка (rework)
    accepted -> done (эпик)     архитектор, когда все наряды эпика accepted и эталонная серия зелёная
    any -> blocked / needs-decision  мотор автоматически, по письму исполнителя
    in-progress -> agreed       мотор автоматически, по просрочке lease_until
    accepted -> rework          архитектор, по [scenario-failed]

Не указанный переход — запрещён. Переход предлагает исполнитель письмом, применяет мотор или архитектор.

## 6. Письма обмена

Формат — dsh-exchange/1, шапка: From/To/Date/Thread/Status/Workspace/Session/Reply-To/Subject.
Session обязателен: сторону определяют по нему, а не по From. Тред: threads/kanban-<EPIC>/.

Маркер перехода — префикс Subject. Набор маркеров:

    [task-accept]        исполнитель берёт наряд (несёт lease_until)
    [interface-proposal] предложение версии контракта обмена
    [interface-agreed]   подтверждение согласования версии
    [stage-ready]        результат стадии готов (несёт evidence)
    [blocked]            заблокирован (несёт причину и что ждёт)
    [needs-decision]     нужен вердикт архитектора
    [scenario-failed]    эталонная серия покраснела (от архитектора)

Ответы мотора (от архитектора исполнителю):

    [transition-applied]  переход применён (from -> to, ссылка на журнал)
    [transition-rejected] отказ (причина + допустимые переходы)
    [duplicate]           письмо уже обработано
    [unknown-card]        карточка не найдена
    [board-repaired]      доска восстановлена из журнала
    [lease-expired]       лиз истёк, наряд возвращён в agreed

Каждый переход подтверждается письмом — исполнитель не гадает по молчанию.

## 7. Журнал (journal.jsonl)

Append-only, одна строка на событие. События: transition, sweep, repair.

    {"at":"ISO-8601","kind":"transition","epic":"E1","card":"E1-1","from":"agreed","to":"in-progress","by":"architect|motor","letter":"threads/kanban-E1/<файл>","proof":"<sha256 письма>","lease_until":"ISO-8601","revision":3}}

Идемпотентность: ключ перехода — <card>:<from>:<to>:<sha256(письма)>. Повтор письма = [duplicate],
повторного перехода нет.

## 8. Мотор (apply, sweep, replay)

apply(card, from, to, reason, letter):
  1. найти карточку; нет — [unknown-card];
  2. проверить допустимость перехода и совпадение from с текущим status и revision;
  3. проверить доказательство (файл письма существует, у готовности есть evidence);
  4. проверить идемпотентность по ключу журнала;
  5. записать карточку (временный файл + rename), затем строку журнала (порядок важен);
  6. ответить [transition-applied] или отказом;
  7. обновить .sweep.json.

sweep (триггеры: таймер, приход письма, перед рендером):
  1. прочитать новые письма из outbox каждого исполнителя (память прочтения в .sweep.json);
  2. применить apply для каждого письма;
  3. проверить лизы: lease_until < now -> вернуть наряд в agreed + письмо [lease-expired];
  4. записать отчёт обхода в журнал (kind=sweep).

replay/reconcile: карточка — материализованное представление журнала. При расхождении status карточки с
последней строкой журнала — авто-восстановление из журнала, строка kind=repair, письмо [board-repaired].

## 9. Конфиг реалма (runtime)

Плагин читает конфиг реалма, который владелец кладёт в воркспейсе архитектора. Схема:

    {
      version: 1,
      architect: { root, exchange },
      workspaces: [ { id, root, exchange }, ... ]
    }

console/proxy/optimizer — пример id; реальные пути подставляет владелец реалма.

## 10. Разделение код/модель

Код (императив, детерминировано): валидация переходов, proof, идемпотентность, запись карточки и журнала,
обход, просрочка лиза, сверка и починка, рендер. Модель (суждение): выбор версии контракта, приёмка стыка,
закрытие эпика, декомпозиция и приоритеты. Модель меняет состояние только через ту же операцию apply,
с записью by=architect.

## 11. Инварианты

- один писатель карточек и журнала — воркспейс архитектора (мотор/сессия);
- письма — каждый в свой outbox, конфликтов записи нет по построению;
- журнал append-only, не редактируется; карточка восстанавливается из журнала;
- любой переход подтверждается письмом и оставляет строку журнала;
- правка состояния в обход apply — дефект, ловится сверкой journal<->tasks.

## 12. Версионирование протокола

Поле version в начале документа и в конфиге реалма. Изменение формата карточки, состояний, маркеров или
журнала — новая версия протокола, а не тихая правка.
